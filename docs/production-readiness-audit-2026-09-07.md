## Блокирующие находки

### A01 — P0: захват устройства через повторную регистрацию (воспроизведено)

`server/PhotoSync.Server/Endpoints/DeviceEndpoints.cs`, `RegisterAsync`, ветка существующего UUID: анонимный endpoint принимает новый произвольный секрет и заменяет старый без его предъявления и без подтверждения владельца. После этого запросы злоумышленника проходят, а старый секрет владельца отклоняется. Нужен известный UUID; это не требует угадывания 256-битного секрета. Если устройство связано с Google-пользователем, последующая аутентификация получает и его user claim.

Проба: чужой клиент сначала получает 401, выполняет register с UUID владельца и собственным секретом, получает 200 при чтении альбомов; владелец получает 401. Существующий `DeviceIsolationTests` допускает такую перерегистрацию, поэтому зелёная штатная проверка не защищает от этой уязвимости.

Исправление: обычная перерегистрация только с текущим секретом; восстановление доступа — отдельный процесс с доказательством владения. Не переносить доверие на знание UUID.

### A02 — P1: ложное подтверждение сохранности оригинала (воспроизведено)

`Services/FileStorageService.cs:27–29` возвращает успех дедупликации по строке SQLite, не проверяя файл. `Endpoints/FileEndpoints.cs`, `DedupResponseAsync`, делает то же для check.

Проба: загрузить тестовый файл, удалить только его физическую копию из временного хранилища, повторить upload. Ответ 200, download остаётся 404. Android после успешного upload запускает политику очистки (`NetworkPhotoSyncRepository.kt:417`), поэтому такой ответ может привести к удалению последнего доступного оригинала после системного подтверждения пользователя.

Исправление: подтверждать доступность и целостность оригинала перед успешной дедупликацией; восстанавливать отсутствующий/повреждённый файл из повтора. Недоступное хранилище должно давать ошибку, запрещающую очистку источника.

### A03 — P1: запись файла и SQLite не согласованы после сбоя (воспроизведено)

`FileStorageService.cs:73,95`: файл перемещён в окончательный каталог до `SaveChangesAsync`; после ошибки убирается только временный файл.

Проба с SQLite trigger, отклоняющим INSERT: upload → 500, строк файлов 0, оригиналов на диске 1. После снятия отказа и повтора: строк 1, файлов 2. Получаются невидимые копии, занимающие место вне подсчёта `MaxStorageBytes`. Прерывание процесса между этими операциями создаёт аналогичное окно рассогласования.

Исправление: явное состояние незавершённой загрузки и восстановление/сверка после сбоя. Не решать проблему безусловным удалением уже опубликованных оригиналов.

### A04 — P1: большие медиа целиком в памяти (подтверждено кодом)

`NetworkPhotoSyncRepository.kt:362` читает весь источник через `readBytes()`. `PhotoSyncApiClient` принимает `ByteArray`, скачивание также возвращает целый массив. Сервер `FileEndpoints.cs:210` использует `ReadAllBytesAsync` и для preview, и для download. Preview фактически отдаёт оригинал.

На больших видео и нескольких запросах расход памяти растёт пропорционально размеру файлов; на телефоне возможен OOM ещё до серверной проверки лимита. Копирование источника в `OfflineFirstPhotoSyncRepository.makeDurableUri` выполняется синхронно без переключения на IO, а вызывается из `viewModelScope`: крупный импорт может блокировать UI.

Исправление: потоковые хеширование/передача/скачивание, ограниченные буферы, отдельные превью; перенос локального копирования на IO. По умолчанию сервер допускает всего 25 МиБ на файл; требуемый предел видео нужно согласовать и проверить вместе с HTTP/proxy-ограничениями.

### A05 — P1: локальная сеть без интернета блокирует очередь (подтверждено кодом)

`OfflineFirstPhotoSyncRepository.kt:237` требует одновременно INTERNET и VALIDATED. Доступный домашний сервер в Wi-Fi без внешнего интернета не удовлетворяет этому условию. Очередь остаётся Pending, хотя запросы к серверу могут работать. `NetworkSyncObserver` также ориентируется на интернет.

`OfflineSyncWorker` считает работу завершённой по `ConnectionStatus.Online`, не по результату очереди. В частности, после успешного refresh локального сервера и пропущенной по этому условию очереди worker возвращает success с оставшимися файлами. Это конкретный путь к потере фонового повтора.

Исправление: проверять доступность выбранного сервера, хранить результаты отдельных заданий, повторять временные ошибки, отдельно показывать постоянные. Дополнительно проверить REPLACE-задачи и отмену корутин при добавлении новых файлов.

### A06 — P1: альбомы разных устройств смешиваются по названию (подтверждено кодом)

`NetworkPhotoSyncRepository.kt:167,184,188`: `distinctBy { it.name }` и `groupBy { it.albumName }` работают по всем устройствам пользователя. Два альбома «Отпуск» на двух телефонах превращаются в одну карточку со смешанными файлами и одним `remoteAlbumId`; отправка и настройка прав могут обращаться к одному из двух альбомов.

Исправление: стабильная идентичность server+albumId, явное сопоставление локального UUID с серверным ID. Если продукт должен объединять альбомы между устройствами, такую модель нужно реализовать на сервере, а не выводить из совпадения имён.

### A07 — P1: очередь не отделена по серверу/аккаунту (подтверждено кодом; нужен интеграционный сценарий)

`OfflineFirstPhotoSyncRepository` использует единственные preferences `photosync_offline_queue_v1`; запись не содержит сервер или владельца. `updateServerUrl` переключает delegate и пытается отправлять прежнюю очередь. При несовпадающих folderId элементы застрянут; при совпадающих ID, например `shared-1` на двух серверах, возможен неверный адресат.

Исправление: включить идентичность сервера/пользователя/альбома в очередь; исключить перенос задания между контекстами без явного действия. Проверить отдельно смену аккаунта, поскольку локальный cache namespace содержит device UUID, но не Google subject.

### A08 — P1: Google ID token и ссылки приглашений попадают в журнал (подтверждено кодом)

`RequestAuditMiddleware.ReadRequestBodyAsync` исключает `/api/auth/google`, но не `/api/family/join/{token}`. Последний принимает JSON с `id_token` (`FamilyContracts.cs`). Для обычного тела до 8 КиБ журнал сохраняет его целиком. Полный path сохраняет токен приглашения; ответ создания приглашения тоже захватывается как JSON.

Это противоречит комментарию, что Google-токены не журналируются. Исправление: явная редакция секретных полей и маршрутов до записи и тесты с синтетическими токенами; ограничить срок хранения журналов. Сам token приглашения дополнительно связан с email, поэтому его утечка не означает самостоятельного обхода этой проверки.

## Остальные важные риски

- **P1, повторная проверка прав использует старый объект альбома.** `FileStorageService` повторно передаёт тот же `command.Album` в `FolderAccessService`. `ArchivedAtUtc`, `SharingMode`, `FamilyPermission` не перечитываются перед публикацией. Изменение WholeFamily → Private или архивирование во время загрузки может не учитываться. ACL и членство, напротив, запрашиваются заново. Нужен тест конкурентного отзыва и согласование проверки с публикацией.
- **P2, очередь не подтверждает долговечность записи.** SharedPreferences `apply()` асинхронен; UI уже принимает файл, а ошибка сохранения не возвращается. При повреждённом JSON `loadQueue` молча возвращает пустую очередь; частичная staging-копия при ошибке не убирается. Нужны атомарная персистентность, учёт ошибок диска и восстановление, а не молчаливое обнуление.
- **P2, неверная дата съёмки.** Клиент передаёт `Instant.now()` как `created_at`, то есть время отправки вместо времени создания исходного медиа. Уточнить требуемую семантику и извлекать исходную дату, сохраняя отдельную uploaded_at.
- **P1 для публичной установки, открытое зачисление устройств.** Register не требует приглашения/админского допуска и больше не проверяет количество устройств. Посторонний может создать свою идентичность и загружать данные в пределах общей квоты. README всё ещё заявляет cap=5. Для публичного адреса нужна политика допуска; ограничение частоты само по себе её не заменяет.
- **Эксплуатационный пробел.** `/health` проверяет только подключение к SQLite. Он не подтверждает доступность нужного диска и оригиналов; `Directory.CreateDirectory` не удостоверяет наличие ожидаемого mount. Для обещания сохранности нужны проверка носителя, мониторинг свободного места и проверенное восстановление резервной копии. Их работа на реальном сервере этим аудитом не проверялась.
- **Пробел CI.** Найденный workflow запускается только вручную; проверяет Android unit tests и debug APK. Нет автоматического PR-gate для сервера, lint и устойчивости. В репозитории также есть второй, не включённый в активную solution каталог серверных тестов: результаты 38 тестов относятся к `server/tests/PhotoSync.Server.Tests`.

## Дальнейшая проверка и критерии приёмки

Сначала устранить A01, A02 и A08; затем восстановление хранения, потоковую обработку, очередь и идентичность альбомов. На каждый исправленный дефект добавить тест, утверждающий безопасный результат, а не текущее поведение диагностических проб.

На телефоне использовать отдельные тестовые фото/видео и тестовые альбомы:

1. Импорт одного файла и пачки через галерею и Share; фото разных форматов и видео до согласованного максимума. Сверять SHA-256 оригинала и скачанной серверной копии.
2. Обрыв Wi-Fi во время передачи, смена сети, локальная сеть без интернета, восстановление соединения. Очередь должна завершиться без дублей и ручного повторного импорта.
3. Закрытие UI, уничтожение процесса, перезагрузка, ограничения батареи/фоновой работы. Не смешивать force-stop с обычным уничтожением процесса: после force-stop отдельно проверить восстановление при запуске приложения.
4. Полный диск телефона/сервера, недоступный том и остановка тестового сервера во время загрузки. Нельзя помечать файл сохранённым и чистить источник при отсутствии подтверждённого оригинала.
5. Два Google-аккаунта, два устройства с одинаковыми именами альбомов; View/Contribute, отзыв доступа, приглашения, выход и смена аккаунта/сервера при непустой очереди.
6. Все режимы очистки: сохранить, сжать, запросить удаление; отмена системного подтверждения и повторный запуск приложения.
7. Обновление поверх установленного APK с сохранением очереди/идентичности и прежней подписью.
8. Восстановление тестового архива из резервной копии в отдельное окружение, сверка числа файлов и хешей.

Для удалённого теста понадобится подключённый к этому компьютеру телефон с разрешённой USB-отладкой. Отдельно нужен доступ к конфигурации реального сервера для проверки диска, proxy, резервного копирования и перезапуска; наличие адреса в исходниках не подтверждает эти свойства.

Ожидаются ответы пользователя: публичный интернет или LAN; максимальный размер видео; должен ли телефон сохранять доступ к приватным альбомам после выхода/смены Google-аккаунта. До ответа это открытые продуктовые требования, а не повод считать текущий доступ корректным.

## Повтор диагностических проб

Из корня проекта, в PowerShell (временный файл назначения должен отсутствовать):

```powershell
$probeTarget = 'server/tests/PhotoSync.Server.Tests/ProductionReadinessProbes.cs'
if (Test-Path -LiteralPath $probeTarget) { throw 'Probe target already exists' }
Copy-Item -LiteralPath docs/audit/ProductionReadinessProbes.cs -Destination $probeTarget
try {
    dotnet test server/PhotoSync.Server.slnx --filter FullyQualifiedName~ProductionReadinessProbes --verbosity minimal
} finally {
    Remove-Item -LiteralPath $probeTarget
}
```

После исправлений пробы закономерно перестанут проходить: они документируют исходные дефекты и не включены в обычную сборку.
