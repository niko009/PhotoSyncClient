# PhotoSync: Google-вход и хранение фотографий в Windows

Зафиксировано: 2026-08-31.

Статус на 2026-09-01: Google-вход и объединение устройств одного аккаунта
реализованы в 0.3.0-beta. Сервер развёрнут на `https://photosync.bacus.dev`.
Подключение Windows-папки и семейные ACL **ещё не реализованы**. Самостоятельный
[доступ по телефону без Google](device-access.md) по-прежнему используется по
умолчанию. Этот документ не подтверждает настройку общей папки.

## Окружение и целевая схема

Владелец подтвердил: хост Windows, виртуальная машина VirtualBox, внутри Ubuntu.
Сервер PhotoSync планируется запускать в Docker через существующий Bacus Agent.
Адрес сервера — `https://photosync.bacus.dev`.

```text
Android: ключ телефона по умолчанию; Google-вход — привязка общего аккаунта
  → HTTPS → PhotoSync в Docker / Ubuntu / VirtualBox
              ├─ оригиналы → общая папка VirtualBox → папка на диске Windows
              └─ SQLite → постоянный локальный Docker-том внутри Ubuntu
```

Изначальный режим одного владельца расширен до семейного сервера с отдельными
Google-аккаунтами. Каждый участник может иметь несколько телефонов; папки личные
по умолчанию, совместный доступ выдаётся явно. Состав семьи и права папок описаны
в [плане семейного доступа](family-sharing.md), который заменяет прежнее ограничение
одним аккаунтом. Публичный многопользовательский платный хостинг в эту схему не
входит. Google используется для входа, а не для хранения фотографий.

## Реализованная авторизация 0.3.0-beta

1. «Войти через Google» в Android работает через Credential Manager.
2. Google ID token передаётся серверу по HTTPS. Сервер проверяет подпись,
   издателя, срок действия и аудиторию — ожидаемый OAuth client ID приложения.
3. Для связи используется стабильный Google `sub`, а не присланный клиентом email.
   Сервер не сохраняет ID token или Google access token.
4. Привязка возможна только из уже аутентифицированного пространства телефона.
   Устройства с одинаковым `sub` видят единый архив; выход отвязывает только
   текущее устройство и возвращает его в приватный режим.
5. Все операции с данными остаются защищены ключом установки. Google расширяет
   область видимости, но не заменяет bearer-ключ для фоновой синхронизации.

Семейные приглашения и права отдельных папок остаются следующим этапом. Веб-портал
использует тот же подтверждённый Google `sub` и автоматически показывает связанные устройства.

Google OAuth настроен для package `com.photosync.android`, release SHA-1 и Web
Client ID. Закрытый ключ подписи и его пароли исключены из Git. Android client
secret не требуется и не должен находиться в APK.

## Подключение папки Windows

Все пути ниже — **примеры**, фактическую папку Windows владелец ещё не выбрал.

1. На Windows создать выделенную папку, например `D:\PhotoSync`.
   Не предоставлять виртуальной машине весь диск или пользовательский профиль.
2. В настройках нужной VM VirtualBox открыть «Общие папки» и добавить:
   - путь Windows: выбранная папка;
   - имя ресурса: `photosync`;
   - автоподключение: включено;
   - только чтение: выключено;
   - ресурс постоянный, не временный на один сеанс VM.
3. Проверить Guest Additions в Ubuntu; при необходимости установить совместимую
   версию. Перезапуск VM с работающими сайтами заранее согласовать.
4. Проверить фактическую точку подключения. При стандартном автоподключении
   ожидается `/media/sf_photosync`. Убедиться, что это действительно файловая
   система `vboxsf`, а не обычная пустая директория Ubuntu.
5. Проверить запись из Ubuntu и появление тестового файла в Проводнике Windows.
   Автоподключённые папки обычно доступны root и группе `vboxsf`.
6. Передать подключённую папку контейнеру через bind mount, например в `/photos`.
   Настроить доступ для непривилегированного пользователя контейнера — например,
   через дополнительную группу с фактическим числовым GID `vboxsf` в Ubuntu.
   Добавление только пользователя Ubuntu в группу не даёт автоматически права
   пользователю внутри контейнера. Проверить запись именно из контейнера.

SMB и открытие сетевой папки в интернет для этой схемы не требуются. После
успешной загрузки оригинал находится непосредственно в папке Windows; отдельная
синхронизация из виртуального диска не нужна. Не перемещать и не переименовывать
управляемые PhotoSync файлы вручную: сохранённые пути в базе могут стать неверными.

## Изменения хранения, которые ещё предстоят

Текущий `compose.yml` сохраняет и медиа, и SQLite в одном томе
`bacus-photosync-data`. **Он ещё не настроен для общей папки Windows.**

Целевое разделение:

| Данные | Место хранения |
| --- | --- |
| Оригиналы фото и видео | Общая папка Windows, доступная контейнеру как `/photos` |
| Временные загрузки | Выделенная подпапка того же хранилища медиа для финального перемещения файлов |
| SQLite, включая WAL/SHM | Постоянный локальный том Ubuntu, например `/data/system/` |

При реализации отдельно настроить `PhotoSync:StorageRoot` и строку подключения
SQLite. Не переносить рабочую SQLite-базу на общую папку VirtualBox. Проверить
реальные пути в StoragePathResolver: нельзя полагаться только на названия опций
TempRoot/PreviewRoot, не проверив их использование кодом.

Существующие фотографии и базы автоматически не переносить. Если данные уже есть,
сначала согласовать миграцию, сделать согласованную резервную копию и проверить
сохранность относительных путей и хешей. Не удалять старый том при переключении.

## Порядок запуска и отказоустойчивость

- Запускать PhotoSync только после подключения общей папки; учесть автоматический
  перезапуск Docker-контейнеров при загрузке Ubuntu.
- Запретить автоматическое создание отсутствующего исходного пути bind mount.
  Одного существования директории недостаточно: проверить само подключение и
  идентичность хранилища, например через контрольный файл, созданный при настройке.
- Если папка пропала, диск переполнен или запись невозможна, не подтверждать
  синхронизацию и не переключаться молча на локальную директорию Ubuntu.
- Подтверждать загрузку только после проверки и сохранения файла и метаданных.
- Windows, VirtualBox и Ubuntu должны работать для доступности сервера. Сон хоста
  и остановка VM прерывают синхронизацию.
- Общая папка не является резервной копией. Нужны отдельный бэкап оригиналов,
  согласованная копия SQLite и проверка восстановления. Снимок VM не заменяет
  резервную копию файлов в общей папке Windows.

## Проверки перед публичным запуском

- [ ] Владелец выбрал папку Windows и разрешённый Google-аккаунт.
- [ ] Проверены версии Ubuntu/VirtualBox, Guest Additions, права и автоподключение.
- [ ] Google-вход работает; неприглашённый аккаунт и запросы без сессии не получают доступ.
- [ ] Семейный режим проходит проверки изоляции, приглашений и прав папок из отдельного плана.
- [ ] Проверены фоновая синхронизация, истечение и отзыв сессии.
- [ ] Файл с телефона появляется в Windows, хеш оригинала и скачанной копии совпадает.
- [ ] Проверены большое видео, обрыв загрузки и повторная отправка.
- [ ] Проверены недоступная папка, ошибка записи и отсутствие ложного успеха.
- [ ] Данные сохраняются после пересоздания контейнера и перезапуска VM.
- [ ] Настроены резервное копирование и восстановление.
- [ ] Устранено ранее обнаруженное предупреждение NU1903 SQLite-зависимости.
- [ ] Только после этих проверок разрешены регистрация домена и публичный запуск.
